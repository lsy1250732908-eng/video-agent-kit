# 从成片反馈到技能升级

## 先判断正在改什么

- 改某条提示词：修复该项目，不自动改变所有未来项目。
- 记录个人偏好：例如“我不喜欢高速运镜”，标为用户偏好及适用范围，不写成通用视频规律。
- 改工具适配：某入口的模式或限制变化，核验现行依据，更新适配参考。
- 升级通用方法：多次可比较结果支持某种做法，或发现明确的逻辑错误，再更新主流程/方法。

用户明确要求“吸收这次经验、升级这个 skill”时执行升级，不需要另建一份失去同步的技能。仅有零散负反馈时，先修本次任务，是否提升为通用规则取决于证据。

## 收集最少但可比较的证据

使用 [实验记录](../assets/experiment-record.md)，尽量取得：实际提示词、真实上传素材/用途、模型与入口、参数、生成结果、用户指出的偏差时间、希望发生的画面。

材料不足仍可提出修订，但标注“根据描述推断”；不要声称看过成片。没有成片也能修明显冲突，例如把全片第 50 秒写进 7 秒任务，这是文本逻辑修正，不需要伪造模型测试。

项目记录保存在用户指定输出目录。技能只吸收必要的经验摘要与可复用规则，不把账号凭据、带签名的下载链接、私有完整视频或无关个人信息收进分发包。

## 定位偏差，不先加词

|观察到的偏差|优先检查|可尝试的单项修改|
|---|---|---|
|角色换脸、换衣|参考冲突、身份绑定、太多同时出现的人物|保留统一身份参考，删除矛盾外观描述|
|动作顺序错|开头状态混入终点、阶段并列、任务过载|把事件改成明确先后因果，减少一个非核心动作|
|镜头乱转|主体运动与相机运动混写|固定主体，单独描述相机路径和终点|
|穿屏变成溶解|缺少边框/遮挡、中间空间不清楚|增加一个中间构图或改为遮挡剪辑|
|球内变平面贴图|内外层关系不清、参考没有展示立体|明确容器边界和内部立体布局，补过程参考|
|局部关机变全片黑|效果作用域不明|限定屏幕区域，列明外部灯光状态|
|总时长对、卡点错|内部事件时刻没有对齐|按事件分段校准，而不是继续整体变速|
|文字标识失真|文字精度超出本次生成结果能力|考虑后期叠加并实测，不承诺靠重复品牌名解决|

这些是诊断假设，不是一对一确定病因。先查看实际结果再选最可能的一项。

## 做能解释结果的对比

一次尽量只改一个主要因素：文字顺序、参考图、任务长度或拆镜策略。记录未改的内容。工具支持固定随机种子时可辅助比较；不支持时如实记录随机性，不能把一次出好片归因于唯一修改。

先验收用户的“必须保留”，再看审美偏好。可用“满足 / 部分满足 / 未满足 / 未验证”记录各项，并给出画面证据或时间位置。不要给没有依据的总分、成功概率或百分比提升。

未获用户生成请求时，只准备对比方案；不为了技能评估自行消耗付费额度。

## 经验分级与晋升

|状态|可作何种表述|存放位置|
|---|---|---|
|观察 O|原片/成片中实际看到的情况|项目记录、案例|
|逻辑修正 L|删除互相冲突的时间、数量或指令|方法或模板；说明未测生成效果|
|假设 H|推测可能更好，尚未对比|项目实验计划、案例建议|
|单次实测 T|在指定入口、素材和参数下观察到改善|案例；保留样本范围|
|重复支持 R|多个可比较结果支持，且未发现明显反例|方法中的条件性建议，注明适用范围|

不按固定次数机械宣称“已证明”。场景是否多样、变量是否受控和结果是否可观察，比次数更重要。单次失败也不能推出“这个模型不能做此类视频”。

## 升级步骤

1. 确认当前版本与文件位置；通过软链接安装时解析真实源目录。
2. 保存将改动文件的旧内容及版本记录，放用户项目目录的版本备份中；不删除已有经验。
3. 写下“问题 → 证据 → 修改 → 适用范围 → 未解决内容”。先更新最窄的案例/适配文件，确需通用化才改 SKILL.md 或方法。
4. 更新 `SKILL.md` 的 metadata 版本/日期，并向 [演进记录](evolution-log.md) 追加条目。
5. 跑结构验证与相关 [行为验收题](evaluation-cases.md)。确认所有相对引用存在，模板与主流程一致。
6. 对用户说明改动、证据等级、验证范围和仍未验证的部分。若有分发 ZIP，重新打包，并核对 ZIP 内版本与源目录一致。

版本约定：文字修正和小范围澄清用补丁号；新增兼容方法/模板用次版本；改变主要输出约定或移除旧工作流用主版本。版本号描述技能变化，不代表模型能力升级。

## 撤回

如果新方法破坏其他场景或用户不接受，依据版本备份恢复受影响的文件，追加撤回说明，不掩盖原结论。安装是软链接时，源文件恢复后本地入口也同步恢复；已经发出去的 ZIP 需另发更正版本。

不要声称“以后会自动后台学习”。只有后续对话实际执行更新，文件才会改变。
